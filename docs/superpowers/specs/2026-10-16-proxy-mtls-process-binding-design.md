# CodexHelper 代理授权设计：mTLS、独立密码与本机进程身份绑定

状态：设计评审稿，待用户批准；未实施、未部署。
日期：2026-10-16
涉及仓库：`CodexHelper`、`mihomo-docker`。

## 1. 意图、范围与安全承诺

用户目标不是只给代理加密码，而是防止授权代理被配置到其他应用里使用，同时让现有 7891 用户平稳迁移。

本设计采用三道检查：

1. 服务端用 mTLS 验证客户端持有受信任的设备私钥，阻止普通网络客户端接入。
2. TLS 内再做 SOCKS5 用户名密码认证，提供独立的账号停用与轮换手段。
3. CodexHelper 在本机代理入口核实真实 TCP 连接所有者，仅允许列入可信策略的 Codex 引擎进程使用；其他程序即使知道本地端口也不能借用隧道。

**明确边界：这不是远程进程证明，也不是对客户端机器所有者的绝对防复制 DRM。** 服务端验证的是证书和密码，不能仅凭 TLS 知道连接来自哪个可执行文件。本机进程检查由受信任的 CodexHelper 执行；拥有管理员权限、可修改/调试 CodexHelper、提取两项秘密、向被允许进程注入代码，或者把被允许进程用作转发器的攻击者，不在本版保证范围内。普通应用不能直接借用代理，不等于被授权应用绝不可能代其他程序转发。

### 1.1 本版支持范围与推荐取舍

以下是设计者建议，尚非用户已批准的决策：

- 新远端端口使用 **7892/TCP**，固定端口便于运维；随机端口不作为安全措施。
- 保留本机 `127.0.0.1:17891`，不改变 Codex 使用 HTTP CONNECT 的方式。
- 同时设计 macOS 与 Windows 适配；各平台分别通过实机门禁后才能标为已支持，不用一侧结果替代另一侧验收。
- 首版不强制购买代码签名证书：客户端及 Codex 引擎使用管理员签发的版本哈希策略；已有可信发布者签名时额外校验。macOS 当前 ad-hoc 签名不能充当稳定发布者身份。
- 首版使用软件客户端私钥，放入系统凭据存储；不宣称不可导出或硬件绑定。Secure Enclave/TPM 为后续独立强化项目。
- 不改变 GitHub 的路由语义，不增加 JA3/JA4 放行，不自动回退旧端口。
- 用**第二个独立 mihomo 实例**承载新端口，不重建旧实例实现所谓“无感新增”。

### 1.2 非目标与反目标

非目标：防 root/管理员、完全防内存提取、远程证明进程未被篡改、TLS 解密目标网站内容、Linux 正式支持、为 Codex 任意子进程自动授权、治理独立的模型网关 8080。

反目标：7892 存在明文或无认证旁路；校验失败自动回退 7891/直连；把代理秘密编译进安装包；以进程名/路径/JA3 代替身份校验；为兼容升级静默关闭进程检查；尚未验证就关闭旧入口。

## 2. 已核实的基线与前述说明修正

- 服务端现有映射是 `0.0.0.0:${MIHOMO_OPENAI_PORT:-7891}:7891`，7890 对宿主机仅回环发布；容器内部 7890 被 sub2api 使用，应保持不变。
- 本地 `config/config.yaml` 的 7891 listener 是 `mixed`、`users: []`，使用 `openai-restrict`；白名单之外拒绝。
- CodexHelper `consts.rs` 的上游是 `10.20.30.61:7891`。`proxy.rs` 只实现无认证 SOCKS5，`connect_upstream`、`tunnel`、`forward_plain` 当前使用具体 `TcpStream`。
- `codex_env.rs` 将 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 指到本地 17891。`rules.rs` 中 GitHub 走直连。服务端放行 GitHub与否不会改变客户端“GitHub 不送上游”的现状。
- macOS 网关 API Key 通过 `/usr/bin/security` 存取；现有设计明确接受同用户进程可借该 CLI 读取的风险。这套后端不提供应用专属访问保证，不能直接声称 Keychain 会阻止同用户程序读取。
- `mihomo-docker/.gitignore` 已忽略 `config/*`。前文“config.yaml 被 Git 跟踪”的说法没有依据；新增的秘密目录仍须单独检查忽略规则，不能因为叫 config 就认定安全。
- SOCKS5 仅提供用户名密码方法时，问候是 **`05 01 02`**，不是 `05 02 02`。后者声明两种方法但只携带一种，是错误报文。
- 普通 curl 的 `socks5h://` 不会自动套上到代理服务器的 TLS；新端口必须用支持 SOCKS-over-TLS/mTLS 的专用探测器验证。
- 已核对 mihomo **v1.19.30** 的 `listener/inbound/socks.go`、`mixed.go` 与 `listener/socks/tcp.go`：具有证书、客户端 CA 与客户端认证配置，实际接入仍需固定镜像实测。
- 当前没有本地运行实例及部署机授权连接证据。下文是设计，不代表生产环境已具备配置、证书或进程识别能力。

## 3. 总体架构与信任边界

```text
被允许的 Codex 引擎
  │ HTTP / CONNECT，127.0.0.1:17891
  ▼
CodexHelper
  ① 根据 TCP 四元组寻找连接所有者
  ② 核实 UID/SID、进程实例、代码签名/版本哈希
  ③ 执行现有域名分流
  ├── 非 OpenAI 域名：本机直连（仍须先通过①②）
  └── OpenAI 域名：
        TCP → 服务端证书校验 → mTLS → SOCKS5 密码 → CONNECT
                                                   │
                                                   ▼
                           独立 mihomo-auth 实例，7892/TCP
                           mTLS 必须成功 + users 必须匹配
                           → openai-restrict → 现有代理节点

其他本机应用 → 17891 → 进程身份不匹配 → 拒绝，不建立任何出站连接
普通远端应用 → 7892 → 缺客户端私钥/密码 → 拒绝
旧客户端     → 7891 → 观察期维持，迁移后关闭
```

设备级秘密与本机进程身份是两层不同信任：不能把客户端发来的 PID、文件哈希、自报 User-Agent 或证书主题中的程序名当成远程可验证的进程身份。无需在协议里增加可伪造的“进程指纹头”。

## 4. 服务端设计

### 4.1 独立实例与端口隔离

在 `mihomo-docker` 中增加 `mihomo-auth`，沿用固定版本镜像与代理节点来源，但使用独立容器名、配置目录、缓存数据库和运行目录。不能让两个实例共享可写 `cache.db`、临时配置或下载路径。新实例只发布 7892/TCP，不发布 7890、控制 API 或 UDP。

只新增启动该服务，不对整个 Compose 栈执行会重建旧 mihomo 的操作。上线前检查目标端口未占用、镜像可离线获得、新容器不会读取 `FORCE_UPDATE` 远程覆盖本地安全配置。旧实例/新实例代理组选择独立，必须验证新实例选择的有效节点，不能假定旧实例的动态选择自动继承。

内部 7890 是另一个信任边界：保留给现有 sub2api，但不得新增外部映射；Docker 网络成员及宿主机管理权限不在本版客户端隔离保证内。

### 4.2 新入站配置轮廓

以下是生成后的部署配置示意，秘密占位符不能直接运行，所有相对路径应由生成器转成容器绝对路径：

```yaml
listeners:
  - name: codexhelper-secure
    type: socks
    listen: 0.0.0.0
    port: 7892
    udp: false
    certificate: /run/codexhelper-certs/server.crt
    private-key: /run/codexhelper-certs/server.key
    client-auth-type: require-and-verify
    client-auth-cert: /run/codexhelper-certs/client-ca-bundle.pem
    users:
      - username: device-<device-id>
        password: <设备独立随机密码>
    rule: openai-restrict
```

选择 `socks` 而不是 `mixed`，因为客户端只需 SOCKS5；关闭 UDP，避免独立 UDP 入口不受 TCP TLS 保护。客户端只发 CONNECT，不能提供 BIND/UDP 接口。固定版本仍支持解析 SOCKS4，但它用空密码验证 USERID，因此所有账号必须使用非空密码，验证其不能成为密码旁路。

注意原生实现会接受 SOCKS5 UDP ASSOCIATE 的控制握手，随后丢弃控制连接数据；`udp: false` 禁止的是实际 UDP listener，并非保证返回“命令不支持”。验收标准是外部不能利用 UDP 中继，而不是要求原生实现拒绝该握手。BIND 应拒绝。如果未来要求控制握手也严格只认 CONNECT，需更换/增加协议网关，不在本版假设中。

客户端优先 TLS 1.3，最低 TLS 1.2；固定镜像若不能显式限制最小版本，要通过协议探测确认默认实现满足要求，不能填写未经该版本支持的配置字段。关闭客户端 TLS 0-RTT；首版禁用客户端会话恢复以简化重认证，不将会话恢复当作绕过吊销的例外。

### 4.3 两道认证的关系与局限

mihomo 原生配置会分别检查“证书由受信 CA 签发”和“用户名密码在 users 中”。**它不会自动检查证书 device-id 与用户名 device-id 相等**，也不提供远程进程证明。

首版接受这两个独立门禁，使用专用客户端 CA，不向非 CodexHelper 设备签发证书，每设备独立密码。只有一个设备时只配置一个账号。多设备时，不能宣称 A 证书+B 密码一定被拒；这是原生实现的明确边界，而非待实现的隐藏承诺。

设备停用至少删除对应账号并终止该实例现有会话；已有设备密码泄露时必须轮换。若将来要求证书与账号一一映射、CRL/OCSP 即时吊销、按证书计量或在其他账号秘密也泄露时仍精确撤销证书，需要另加能读取证书身份的认证网关，本版不引入自研网关。

### 4.4 出站规则

迁移时保持现有 `openai-restrict` 行为，不顺便增删白名单，以便定位问题；新老实例读取各自的规则快照并记录摘要。

收口前单独审核宽规则：`DOMAIN-KEYWORD,openai` 能匹配非官方域名；ASN/IP 与第三方整域授权扩大了滥用面。收紧属于单独批准的策略变更。当前白名单不是“仅可用来运行 Codex”的证明，同一获准域名上的其他服务仍可能可达。

默认不放行 GitHub。正常 Codex 引擎访问 GitHub仍按客户端现有规则直连；其他程序通过 17891 访问任何域名都先被进程门禁拒绝。

## 5. 身份、密码与秘密来源

### 5.1 唯一来源与注册

不在每个安装包里放相同证书或密码，也不从 MAC 地址、序列号、machine-id 等公开设备指纹推导秘密。

首版采用小规模人工审批注册：

1. 客户端首次注册生成随机 `device-id` 和独立私钥，生成 CSR。私钥不上传；重装默认视为新注册，不悄悄恢复历史身份。
2. 管理员核对申请人和设备，以离线客户端 CA 签发带 `clientAuth` EKU 的证书，并生成独立随机 32 字节、十六进制编码的 SOCKS5 密码。用户名 `device-<id>`，用户名密码各限制 1–255 字节。
3. 管理端登记：device-id、证书序列号/公钥摘要、账号、有效期、状态与凭据版本。CA 私钥离线保管，不进容器、客户端、仓库或 CI 普通产物。
4. 管理员先部署新账号，再通过独立受控渠道交付密码与注册包。注册包含客户端公证书、服务端信任锚、端点、有效期、策略及管理签名，不含客户端私钥。密码不通过当前明文 8080 或公开下载链接发送。
5. 客户端验证管理签名、CSR 公钥匹配、用途与有效期后，将秘密写入系统存储，执行端到端健康检查，全部成功才激活 Secure 模式。

管理签名公钥可随应用分发，它是公开信任锚而非秘密；管理签名私钥与 CA 私钥分开保管。注册 CA 私钥是证书签发权的源，管理记录是授权状态的源，Keychain/Credential Manager 是客户端秘密的本地存储，不会凭空创造“只属于这个程序”的属性。

### 5.2 本地存放与读取

| 数据 | macOS | Windows | 性质 |
| --- | --- | --- | --- |
| SOCKS5 密码 | 新 generic password：service `codex-helper/proxy-password/<device-id>` | 独立 Credential Manager target | 可在本机解密的秘密；同用户强对手可能读取 |
| 客户端软件私钥 | 独立 OS 凭据项 `codex-helper/proxy-key/<device-id>` | 独立凭据项，检查平台大小上限 | 首版软件密钥可提取，不宣称不可导出 |
| 公证书、服务端 CA、管理策略 | 应用数据目录的已签名注册包 | 同左 | 非秘密，加载时必须验证签名与版本 |
| 网关 API Key | 现有 `codex-helper/managed-gateway` | 现有 target | 不混用，不改变现有读取协议 |

首版使用体积可控的 P-256 私钥编码；秘密条目分别存放，不将大段 PEM 生硬拼进现有 2048 字节限制的 `security -i` 命令。复用凭据接口时保留现有字符/长度检查；超限直接失败，不静默截断。软件私钥若用紧凑编码存放，需要在秘密内存中解码后交给 TLS 库。

只有 CodexHelper 代理后端需要读取代理秘密；现有 `codex-helper-credential get` 的固定 target 白名单保持不变，不增加“导出代理私钥/密码”的 CLI 或前端接口。但这只减少主动暴露面，**不能阻止当前 macOS security 后端或同用户 Windows 程序绕过应用接口读取**。

生产路径只认系统存储，不增加环境变量、命令行密码、明文 JSON 后备或二进制内置密码。内存包装脱敏并尽力清零，不承诺清除 TLS 库的一切副本；日志、崩溃报告、UI 均不展示秘密。

### 5.3 TLS 校验与轮换

- 连接地址可继续是 `10.20.30.61`，但 TLS ServerName 使用管理员指定的真实服务身份；服务端证书的 SAN 必须匹配该 DNS 名，或明确匹配 IP SAN。禁止跳过证书/主机名校验。
- 客户端仅信任部署下发的服务端 CA，默认不额外信任用户代理软件安装的系统根；服务端 CA 与客户端 CA 使用不同用途，避免互信混淆。
- 推荐客户端证书有效期 90 天，提前 14 天提示管理员续签。信任锚轮换使用新旧公钥短期重叠，明确到期时间，不能永久扩大信任集合。
- 秘密更新采用 pending→probe→active 两阶段；失败保留上一套有效 Secure 凭据，不退回 Legacy。管理员允许旧新密码短时重叠时采用临时版本化账号，验证后删除旧账号。
- 撤销默认针对新连接不够：紧急停用要显式终止已建立隧道。首版可重启新实例达到这一点，接受其他 Secure 用户重连；不得声称只改 users 就已断开现存连接。

## 6. 本机“进程特定指纹”的定义

### 6.1 授权单位

不是 PID、进程名、路径单项，也不是 JA3/JA4。授权单位为：

```text
连接 TCP 四元组 + OS 连接所有者
  → UID/SID + PID + 进程启动标识
  → 正在运行映像的实际身份
  → 管理签名策略中的已批准程序版本
```

首版只允许真实发起代理连接的 Codex 引擎版本；不允许浏览器、curl、Python、Node 或所有 Electron 进程。父进程叫 Codex 不构成授权，Codex 启动的 shell/工具子进程也不自动获准。父链可用于诊断，不是放行依据。

已有文档中的 macOS 引擎路径仅是定位线索：`ChatGPT.app/.../codex-cli/CodexCLI.app/.../codex`。应验证实际 GUI 对话、终端 CLI、多进程模型分别由哪个映像连接；如果实际连接者不在设计假设内，先补受控策略再发布，不能放开整个应用目录。

这一限制可能阻断 Codex 工具子进程继承 `HTTP_PROXY` 后访问网络，是本版有意的安全取舍；验收必须记录影响。工具确需代理时，要新增明确程序授权，而不是默认信任所有后代。

### 6.2 程序策略与可信来源

管理签名策略至少包含：policy-id、单调版本、有效期、平台/架构、允许角色、代码签名要求（如适用）、已批准可执行映像 SHA-256、允许安装位置约束及哈希算法版本。路径只用于限制候选位置，不单独授信。

- macOS：验证正在运行进程的动态代码身份与有效签名；存在可靠发布者时验证指定 requirement（含 identifier、Team ID 和受信签名锚），不能只检查 Team ID。ad-hoc 或无稳定发布者时，用管理员批准的各架构映像哈希做版本授权；签名有效本身不代表可信。
- Windows：由 OS 取得进程映像，验证实际文件的 Authenticode（如有）及策略指定发布者/角色，并要求版本哈希命中。无可靠发布者的 Codex CLI 仍可走明确的管理员哈希白名单。
- 不采用首次遇到自动信任、不让 UI 的“允许一次”绕过策略、不从可写目录扫描后自动学习。新版本的批准哈希必须来自管理员独立核验过的产物。
- Universal Mach-O 哈希格式必须固定：分别记录各架构切片的代码身份与用于校验的文件摘要；文件替换与签名/摘要不一致时拒绝。
- 客户端自身也在分发策略中记录版本；这帮助运维核查，但不能靠客户端自校验对抗本机管理员修改程序。

### 6.3 每条连接的校验顺序

1. accept 后记录本地/对端四元组，只接收预期回环地址；不信任 HTTP 请求中的 PID/指纹。
2. 在读代理请求、域名分流和任何目标出站之前做身份核实。设置并发、排队与检查超时，防止扫描耗尽线程。
3. 查询连接所有者，只接受唯一确定的本机连接方；同时核对 UID/SID 与用户作用域，排除服务端自身 socket 误匹配。
4. 打开/固定进程身份句柄或等效实例标识，取启动时间，验证映像与策略；在授权提交前再次确认该进程实例仍拥有同一连接。
5. 检查未知、权限不足、所有者退出、PID 重用、文件不一致、哈希/签名失败都拒绝。默认不拿路径相同的新磁盘文件替运行中旧映像背书。
6. 通过后才解析请求并建立直连或安全上游。不通过者返回最小化 403 或直接关闭；不得产生任何远端连接。
7. 连接准入结果绑定该连接；不能用“某个 Codex PID 在线”全局解锁端口。策略撤销时，关闭受影响的已授权本地连接及对应上游隧道。

缓存仅用于昂贵映像验证，按进程实例、文件身份、策略版本键控；每条连接仍核对 socket 所有者。策略更新、进程退出、文件变化立即失效；不能仅以 PID/路径缓存。

已有自识别健康端点可在门禁前返回最小固定标识，只用于诊断，**不是端口归属、安全版本或 Secure 状态的可信证明**；它不得返回秘密、凭据状态、进程清单，不能转发数据或解锁普通代理请求。其余管理功能使用进程内调用，不以“本地来源”免检。

**Secure 模式必须独占本地后端，不复用 External 代理。** 现有 `Manager::ensure_proxy` 根据公开固定探测应答复用另一进程、并标记为 `ProxyState::External` 的分支，在 SecureReady/激活/启动对账中必须禁用。只有当前 Manager 持有并能配置、排空与停止的 `ProxyHandle`，以及同进程可核实的安全配置/策略版本，才算可用后端。17891 被其他进程占用时阻止激活，提示退出旧 CodexHelper；不得杀死未知占用者、自动换端口或信任它自报已安全。当前进程已有 Legacy handle 时必须完成受控切换与排空，不能仅因 handle 存在就声称 Secure 已运行。

### 6.4 平台实现与强制技术门禁

macOS 候选实现是通过 libproc 的进程/fd/socket 查询按四元组定位连接方，再通过 Security.framework 动态代码 API 校验运行进程。**普通 TCP 没有可直接照搬 Unix socket peer credentials 的跨平台接口**；不能假设某一次进程表扫描就构成无竞态证明。

Windows 候选是 `GetExtendedTcpTable`/IPv6 对应表得到连接方 PID，持有进程句柄并核实创建时间、映像与签名。必须验证权限、IPv4 映射、短连接与 PID 重用行为。

写实现计划前先做受控技术验证，不把候选 API 写成已验证能力：

- 覆盖真实受支持 OS、GUI/CLI、快速连接与退出、端口复用、同用户权限不足、映像更新/exec 竞态。
- 证明不会把服务器自己、同名程序、替换后的磁盘文件或 PID 复用者误认为允许的程序。
- 建议性能目标：本机测试 100 条并发建立连接，身份核实 P95 ≤100ms，单连接总门禁超时 1s；超时拒绝并给出诊断，不自动放行。数字是设计预算，实测后可调整，但不能用误放行换性能。
- 若用户态实现不能达到上述身份一致性，**该平台 Secure 模式不得发布**。再单独评审特权服务、Windows WFP/macOS Network Extension 等方案的安装/签名/权限成本，不能静默降级为进程名检查。

首版不请求 root/管理员常驻服务来掩盖 API 不确定性，也不声称用户态检查能阻止恶意进程把已授权 socket 句柄传给别人。升级为更强 OS 级 enforcement 需另行批准。

## 7. 上游传输与客户端模块改造边界

新模式只使用以下序列：

```text
TCP connect（超时）
→ TLS：验证服务端身份，提交客户端证书并完成私钥签名
→ SOCKS5 greeting：05 01 02（只提供用户名密码）
→ server method：必须为 05 02，否则失败
→ RFC1929：01 ULEN USER PLEN PASSWORD
→ auth reply：必须为 01 00
→ CONNECT（目标域名由上游解析）
→ 转发原业务数据
```

TLS 内仍为标准 SOCKS5；拒绝无认证协商、截断响应、认证失败、证书错误。任何阶段失败都不发目标 CONNECT/业务数据，不重试明文或旧入口，不向目标直连。

`proxy.rs` 不能只在 connect 函数外包 TLS 就结束：隧道与明文转发当前依赖具体 `TcpStream`，需引入统一的 `AsyncRead + AsyncWrite + Unpin + Send` 传输抽象，支持直连 TCP 和 TLS 上游，保留首包 extra 字节、半关闭、流式长连接、超时、停止与连接记录语义。TCP 特有选项在包 TLS 前设置。

建议职责边界（文件名可由实现者调整）：

- `proxy.rs`：HTTP 入口、先授权后分流、隧道生命周期。
- `peer_identity/`：连接所有者查询与平台映像证据，不含业务白名单。
- `process_policy.rs`：纯策略判断、管理签名与版本规则、缓存失效。
- `upstream.rs`：TLS 与 SOCKS5 认证、统一传输、阶段错误。
- `proxy_identity.rs`：注册包、系统秘密读取、凭据版本，禁止前端导出秘密。
- `manager.rs`：注册/激活/轮换/撤销事务与状态；Secure 禁用 External 复用，校验自有 handle 的模式与策略版本；现有网关 Key 生命周期不混用。
- `tests/proxy.rs` 及平台专项测试：fake 身份解析器、真 TLS/认证上游、故障与竞态用例。

无需向本地代理 URL 写上游密码，也不要求 Codex 本身支持客户端证书。依然由 CodexHelper 负责 mTLS，上游凭据不进 `~/.codex/.env` 或 `config.toml`。

## 8. 生命周期、升级与可观测性

### 8.1 状态机

```text
Legacy（现有用户）
  → EnrollmentPending（注册包/秘密校验中）
  → SecureReady（身份门禁与端到端探测均通过，尚未激活）
  → SecureActive
      ├─ 证书/密码/策略异常 → SecureBlocked
      └─ 显式停用 → Disabled
```

新用户不能默认落入 Legacy。已有用户在迁移窗口可继续 Legacy，但 UI 明示“旧入口未受本设计保护”。进入 SecureActive 后，失败只进入 SecureBlocked，不能自动回 Legacy。迁移前 Legacy 的持续可用不等于其具备安全隔离能力。

UI 展示：设备 ID、公证书到期日、策略版本、进程门禁状态、安全入口状态、拒绝原因及修复动作。不提供代理密码查看、复制、导出功能。

### 8.2 更新与撤销

- 新 Codex 版本先批准映像策略，再升级；新旧版本允许在有限窗口共存。未知版本默认拒绝，提示“该引擎版本未授权”。
- 管理签名校验失败、过期策略或策略版本倒退拒绝激活。版本状态使用系统存储持久化；不声称能抵御管理员回滚整台设备状态。
- CodexHelper 更新需兼容秘密 target 和注册包 schema；不迁移成明文。卸载和“停用受管模式”不等于服务端撤销，UI 要区分；“注销设备”应要求管理员完成账号停用。
- 紧急撤销：先停服务端账号并断会话，再删除本地代理秘密；删除网关 API Key 是另一操作。

### 8.3 审计与限额

本机日志记录决策、错误阶段、策略版本、进程角色和脱敏的目标主机；不含密码、私钥、Authorization、完整 URL 查询串或 TLS 库原始秘密错误。拒绝日志限速。

服务端至少能根据认证账号区分 Secure 流量；不假定现有 mihomo 日志能直接打印客户端证书指纹或本地进程。首版采用网络层全局并发/连接速率上限与拒绝日志监控；精确每设备带宽配额属于扩展，不把未实现计量当作防滥用保证。

## 9. 平稳迁移与回滚

### 9.1 阶段与完成条件

| 阶段 | 操作 | 进入下一阶段的证据 |
| --- | --- | --- |
| A 技术验证 | 平台进程所有者验证；固定镜像 mTLS/密码/拒绝测试 | 两层能力均通过对应平台门禁 |
| B 并行上线 | 新建独立 mihomo-auth，发布 7892/TCP；旧容器不重建 | 旧 7891 长连接与旧用户业务持续，新入口负例均拒绝 |
| C 客户端注册 | 安装新版、签发每设备身份、下发管理策略 | 秘密与私钥不在安装包、业务配置、日志中 |
| D 单设备灰度 | 手动激活 Secure；本地进程门禁启用 | 真 Codex 成功；curl/同名程序失败；旧长连接按下述方式排空 |
| E 分批迁移 | 清点使用旧入口的设备；默认观察至少 7 天 | 全部目标设备登记；有可靠证据确认旧入口已无合法使用 |
| F 收口 | 防火墙先拒 7891 新连接，排空后删旧 listener/映射 | 外部探测确认 7891 不可达；7890/sub2api 未受影响 |

激活 Secure 时，配置快照原子替换；旧本地连接不交接 socket。建议给旧连接最多 5 分钟排空，随后关闭并由 Codex 重连，避免旧隧道永久绕开门禁。UI 明示激活完成前的排空状态。安全保证从旧连接全部关闭且 SecureActive 生效时计算。

“7 天无日志”本身不够：旧日志可能不足以定位用户，需结合连接观测、设备清单与使用者确认。观察期对旧 7891 尽可能加现有来源 IP 限制，不能把旧开放口保留误写成已完成安全目标。

### 9.2 回滚

- 收口前：新入口故障不动旧实例；仅管理员批准的迁移回滚可将指定设备显式恢复到 Legacy，记录原因、期限与风险。绝不让客户端自动回退。
- 客户端新凭据探测失败：不切换 active；已有 Secure 客户端继续使用上一套仍有效的 Secure 身份。
- 收口后：优先回滚到上一版安全服务/安全客户端配置，不能自动重开无认证 7891。重新开放旧口属于紧急变更，需用户明确批准并限定来源/时间。
- 设备已撤销的凭据不能因回滚而复活；回滚清单必须带当前撤销状态。

## 10. 验收矩阵与发布门禁

| 场景 | 必须结果 |
| --- | --- |
| 真正允许的 Codex 引擎，本机身份+证书+密码均有效 | OpenAI 业务与流式响应成功 |
| 其他应用/curl 直接用 17891 | 拒绝；直连和上游均未建立 |
| 伪造进程名、路径、请求头 PID、JA3 或父进程名 | 不获准 |
| 旧/伪造代理占用 17891 并返回固定自识应答 | Secure 激活/对账失败，不进入 External 复用，不声称受保护 |
| 本进程已经持有 Legacy handle | 完成配置切换与排空后才进入 SecureActive，不能无条件复用旧模式 |
| 无法取得所有者、多个候选、权限不足、超时 | 拒绝，有稳定错误码 |
| PID 重用、进程退出/exec、映像替换、版本未知 | 不错放；允许可诊断的保守拒绝 |
| Codex 工具子进程继承代理环境 | 未明确批准就拒绝，并记录兼容性影响 |
| 远端只带密码、只带证书、错误/过期证书、错误密码 | 均不能建立目标隧道 |
| 普通 TCP/SOCKS/HTTP 直接打 7892 | TLS/协议层失败，没有明文旁路 |
| 伪服务端、错误 SAN、系统新装根 CA 的中间人 | 客户端拒绝，不发送 SOCKS5 密码 |
| 服务端试图选择 SOCKS5 无认证方法 | 客户端拒绝，不降级 |
| 抓取客户端到服务端流量 | 只见 TLS 加密应用数据，不能直接读出代理密码/业务内容；不承诺隐藏 IP、时序等元数据 |
| 未授权进程访问 GitHub 等直连域名 | 仍被本机门禁拒绝 |
| 获准 Codex 访问 GitHub | 沿用直连；服务端不新增放行 |
| 合法认证后访问白名单外目标 | 服务端拒绝 |
| UDP、BIND、UDP ASSOCIATE、SOCKS4 | 没有可用 UDP 中继；BIND 拒绝；SOCKS4 不可绕过非空密码；不把 UDP 控制握手成功误当作中继开放 |
| TLS/密码/策略任何失败 | 不自动直连或切回 7891 |
| 设备停用或策略撤销 | 新连接拒绝；旧隧道按撤销操作关闭 |
| 发布/安装/本机日志/仓库扫描 | 无共用秘密、私钥、密码和生产注册包 |
| 新服务启动、单机灰度、回滚 | 未迁移设备及 sub2api 不受容器重建影响 |
| 长连接、首包额外数据、半关闭、停止/重启、100 并发 | 无截断、卡死、资源泄漏；满足门禁预算 |

自动测试使用测试专用 CA、账号和系统凭据 target，绝不操作生产 Keychain 条目。协议负例要检查目标服务确实没有收到连接，不能只断言客户端报错。上线工具须真正支持 mTLS+SOCKS-over-TLS；测试 CA/私钥仅用于可重复夹具，不得复用为生产信任锚。

不把以下现象误报成测试失败或成功：本机所有者可通过现有 OS 凭据后端提取秘密是已知边界；A 设备证书+B 设备有效密码可能通过原生 mihomo 是已知边界；只有基础 HTTP 状态码不能证明 mTLS 与进程门禁都有效。

## 11. 交付划分与审批边界

本次交付仅本文，不执行证书签发、业务改造、远端登录、容器重建或防火墙变更。

设计获批后才能编写实施计划，建议依赖顺序：

1. 平台身份识别与固定镜像协议技术验证，决定是否存在必须升级的架构门禁。
2. 本地进程门禁、可信策略、统一传输抽象与认证测试。
3. 设备注册、秘密存储、轮换、状态机与 UI 诊断。
4. 服务端独立实例、部署配置生成、探测及回滚工具。
5. 真机灰度、旧口排空、清点、分批切换与经批准收口。

若要求“即使使用者能读取 Keychain、修改程序，也绝不能被其他应用用”，需要改为受保护的系统 broker/硬件密钥、OS 网络策略及更严格的受管设备模型；不是加一项 TLS 指纹就能补足，本版不得承诺该目标。
